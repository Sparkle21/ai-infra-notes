## 一、问题定义

查询优化器四十年沉淀出的三件套：
1. **代价模型**：用统计信息估算每个物理计划的成本；
2. **计划枚举**：等价空间里系统性搜索（join ordering / DP / branch-and-bound）；
3. **运行时自适应**：AQE——执行中发现估算错了就换计划。

## 二、三个落差（正文主体，每个一节）

### 落差 1：融合决策没有代价模型

- 现状证据：W2 的行为实验 + post_grad.py 源码（决策只看消费者类型，不看形状/带宽）；
- 我验证过的成本语言：W6 的 HBM 趟数账本（「fused 快不快」其实可以算出来）；
- 可移植的想法：把 W6 账本做成 Inductor 的粗粒度 cost gate——小形状退回 eager；
  （预期反驳：编译期不知道运行时形状 → 用 guard 的特化点做，W1-03 的知识）

### 落差 2：并行策略（TP/PP/DP）没有枚举

- 现状证据：S2.5 的 all-reduce 观察 + vLLM 配置项现状（人工选 TP 度）；
- 我验证过的通信成本直觉：通信量随 TP 度 × 上升、随消息大小变化（S2.5 Q3）；
- 可移植的想法：TP/PP 度的枚举空间很小（几个整数组合）——恰好是 DP join ordering
  的迷你版；cost 输入用 ____（roofline 账本 + 实测通信带宽）。
- 边界：KV cache 占用与 batch 的耦合让 cost 不再可加——这是与数据库不同的地方（诚实写）。

### 落差 3：调度没有 runtime feedback 环路

- 现状证据：W3 侦察第 5 问（大概率：chunked prefill 预算、preempt 策略全是静态配置）；
- 我验证过的「反馈值多少」：W3 模拟器 B vs C 的数字（continuous 的收益量化）；
- 可移植的想法：AQE 的三步（collect stats → re-plan → swap）平移到调度：
  用 block 水位与 TTFT 分布在线调 chunk 预算；
- 数据库已踩过的坑直接预警：AQE 的 plan 抖动问题在调度里会变成 KV 反复换入换出。

## 三、量化这条线怎么接上（W9 本周阅读的产出）

- scale 的采集-存储-消费链路（02_kernel_reading_map 第 2 问的答案）与
  **统计信息的生命周期**同构；dynamic 校准 ≈ runtime stats 的「懒采集」；
- 量化 kernel 选择（有/没有 shape 分支）是落差 1 在另一个 subsystem 的复现——
  说明这不是孤立缺失，是系统性的。
