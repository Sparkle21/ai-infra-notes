# LLM 推理栈的三处空白：代价模型、策略枚举与运行时反馈

> **摘要**：LLM 推理栈在短短三四年里长出了完整的一套——serving 调度、KV cache 分页、编译器、手写 kernel 生态——工程密度惊人。但如果把这套栈当作一个整体系统审视，会发现一个规律性的现象：**所有关键决策点，要么是手工经验，要么是写死的启发式；唯独没有"用代价估算来选策略"的机制**——先算账、再拍板的那一步，处处缺席。本文沿"负载本质 → 栈的分层 → 三处空白 → 三个深潜点"的主线给出一个系统分析，并附一个十周动手验证计划。文中论断凡属我的判断而非定论的，均已标注；十周后我会用亲手测到的数据写第二篇。

## 一、缘起

我的背景在数据库内核（执行器、优化器一系），最近半年转看推理栈。这个背景带来的职业病是：拿到任何系统，先找它的"代价估算在哪（每个候选方案算一笔‘多快/多贵’的账）、策略在哪选的（几个方案之间谁拍板）、执行中有没有反馈（跑起来的实际数据会不会反过来修正决策）"。

带着这三个问题读 vLLM、torch.compile/Inductor 和 FlashAttention 系列的源码与论文，最强烈的观感不是"它们缺什么"，而是**缺的位置高度一致**：每一层都把"状态"做得很动态（batch 逐 step 重组、KV 逐块分配、kernel 逐形状特化），但所有"策略"都是静态的（调度规则写死、融合规则写死、并行度手工配）。

一句话概括本文论点：**状态是动态的，策略是静态的**——这中间缺的那块东西，成熟系统里叫优化器。

## 二、推理栈速览：一条请求的完整旅程

先把对象摆齐。一条 chat 请求在典型推理服务（vLLM/SGLang 一系）里的旅程：

```
请求到达 → 排队（waiting）
        → prefill：一次 forward 并行吃掉全部 prompt token，产出第 1 个输出 token，
                   同时按层写入 KV cache
        → decode 循环：每步 forward 产 1 个 token，KV 每步追加
        → EOS（终止符），释放 KV，返回
```

先翻译五个高频词，后文不再解释：**forward** = 把模型完整跑一遍；**prefill**（读题）= 一口气算完整个提问；**decode**（答题）= 之后每步只产出一个 token（词元，模型的最小输出单位）；**KV cache** = 模型逐层存下的"上下文记忆"，随对话变长而变大、必须常驻显存——后文所有显存故事的主角；**kernel** = GPU 上一个可执行的小函数，"这一步怎么算"的完整指令（马上在下表出现）。

支撑这条旅程的是三层，各自职责清楚：

| 层 | 代表 | 职责 | 决策点 |
|---|---|---|---|
| serving 层 | vLLM / SGLang | 调度、batch 组装、KV 内存管理、并发 | 谁进 batch、抢谁的 KV、chunk 切多大 |
| 编译层 | torch.compile / Inductor | 模型定义 → kernel 序列 | 哪些算子融成一个 kernel |
| kernel 层 | Triton / CUDA（FlashAttention、量化 GEMM…） | 单个算子的极致实现 | 用什么 tiling、走 Tensor Core 还是 CUDA Core |

三层合起来看，它就是一个请求处理系统：排队、计划、执行、内存管理样样俱全。而它面对的负载，有两个非常独特的性质——一切的复杂性都从这两个性质里长出来。

## 三、负载的本质：两条硬约束

### 3.1 约束一：prefill 与 decode 的"二象性"

同一个 transformer，两种执行形态的最优资源用法完全相反（以下为纸面推算，实测对账在我的验证计划 W5–W6）：

- **prefill 是 compute-bound**（算力受限：算力先到顶，喂得越饱越划算）。一次 forward 吃 P 个 token，GEMM（矩阵乘，模型的头号计算）的 M 维 = P。P 在千级时，算术强度（每从显存搬 1 字节能换多少次浮点运算）轻松越过 roofline 拐点（算力与带宽两条瓶颈线的交点：左侧喂不饱算力，右侧喂不饱带宽）。
- **decode 是 memory-bound**（带宽受限：数据搬运先到顶，算力大量闲置），而且是结构性的。decode 每步 M 维 = batch size（个位数到几百），GEMM 退化成 skinny GEMM（瘦矩阵乘：行数极少的矩阵乘）。算一笔最直观的账：**每生成一个 token，模型全部权重都要从 HBM（GPU 显存，数据的大仓库）搬一遍**。FP16 下每份权重 2 字节、贡献 2 FLOP（乘+加），算术强度 ≈ 1 FLOP/Byte；batch 为 B 时 ≈ B FLOP/Byte。以 H20 为例（纸面：BF16 峰值约 148 TFLOPS——每秒百万亿次浮点运算、HBM 带宽约 4 TB/s），拐点约 37 FLOP/Byte——**decode batch 不到约 37，算力就是结构性闲置的，且加 batch 几乎线性涨吞吐**（在 KV 显存允许的前提下）。

这个 1 : 37 的落差解释了推理栈一半的设计：为什么 decode 阶段的头号工程问题是"把 batch 做大"（continuous batching——连续拼车，5.1 展开——的由来），为什么 KV cache 管理如此核心（batch 的天花板由显存决定），为什么 prefill/decode 混跑互相伤害（一个抢算力、一个抢带宽，同一时刻硬件的最优用法相反——chunked prefill，把长提问切成小块分步喂、避免一次吃太长把 decode 挤停，正是为了驯服这种干扰）。

### 3.2 约束二：KV cache 是显存账本的主角

KV cache 的显存开销按 token 线性增长：

$$\text{KV 字节/token} = 2 \times n_{layer} \times n_{kv\_head} \times head\_dim \times \text{dtype 字节}$$

以 Llama-2-7B（32 层，按未启用 GQA——一种砍 KV 头数来省显存的技术——的原始配置）FP16 为例：\( 2 \times 32 \times 32 \times 128 \times 2 = 512 KB/token \)。4K 上下文约 2 GB，32K 上下文约 16 GB——**超过权重本身（14 GB）**。而权重是常驻的、不可逐出的，能动的只有 KV。于是"显存怎么在 batch 数量和上下文长度之间分配"成为 serving 层的中心问题。

两条约束叠加，得到推理调度的根本困境：**要吞吐就得堆 batch，堆 batch 就吃显存，显存吃紧就得牺牲某些请求**——牺牲谁、怎么牺牲，这就是调度层的全部戏份。

## 四、三处空白

对照这套负载，逐层检查推理栈的决策机制，会发现同一个模式重复出现。我把它总结为三处空白：

**空白一：融合决策没有代价模型。**（融合 = 把相邻算子合并进同一个 kernel，让中间数据不落显存——收益的账见 5.3。）torch.compile 的 Inductor 后端做融合决策的主体是规则：pattern 表做子图替换、按算子类型（逐元素/归约/外部调用）分组切 kernel。规则引擎本身没问题，问题是它看不见形状：同一条算子链，在小张量（kernel 启动开销主导）和大张量（HBM 带宽主导）下的最优组织方式不同。max-autotune 模式引入了对候选 kernel 的实测调参（把候选挨个跑一遍、掐表选最快），但那是**算子级**的局部择优，不参与"哪些算子融成一个 kernel"这类计划级决策。（此判断基于源码阅读与官方文档，属于我要亲手验证的第一批假设。）

**空白二：并行策略没有枚举。** TP/PP/DP/EP（张量并行——把单个大矩阵切到多卡同算；流水线并行——模型按层分段、各卡接一段；数据并行——各卡跑各自的请求；专家并行——把 MoE 的专家散到多卡）的度数今天是工程师按经验配置的。而 TP 的代价结构相当清楚：每层 forward 一到两次 all-reduce（各卡算完自己那片、再互相合并对齐的一次集体通信——TP 的固定税），通信量随 TP 度线性上升、单卡计算被切小、显存被摊薄。这是一个**枚举空间很小的组合优化问题**（几个整数维度），却没有任何系统机制去搜它——缺的不是研究，是把"代价估算"接到"策略选择"上的那根线。

**空白三：调度没有运行时反馈环。** vLLM 调度器的三个招牌机制——continuous batching、chunked prefill、preemption（抢占：显存告急时把某个正在跑的请求"请下车"，腾出它的 KV 救场）——本质都是写死的启发式：chunk 预算是静态配置，抢占规则是固定策略，准入水线是常数。对比一个理想闭环"收集统计 → 重估策略 → 切换"，推理调度只有第一步"收集状态"是动态的（batch 组成、KV 水位），**策略本身从不随统计变化**。

三处空白形状一致：**都有精确的代价结构（可估算），都有小的决策空间（可枚举），但都没有接上**。这不是巧合——我的判断是：这个领域太年轻，还在"每代硬件重写一遍"的阶段，方法论沉淀排在生存之后。

（顺带一句给同背景的读者：这套"估算-枚举-反馈"的三件套，正是数据库优化器四十年的积累所在；数据库人读推理栈会有大量既视感，但本文不再展开这条线。）

## 五、三个深潜点

### 5.1 decode 的带宽困境与 continuous batching 的天花板

3.1 节的账决定了：decode 阶段唯一的出路是把 batch 做大，摊薄权重搬运。最早的 static batching 要等凑齐一批、跑完最长的才换批，尾随浪费严重；Orca（OSDI'22）提出 iteration-level scheduling——调度粒度从"一批"细化到"一次 forward"——每一步都允许请求完成即离开、新请求即插入。vLLM 把它做成了工业标准。

但注意这套机制反馈的层级：**每 step 变的是"批成员"，不变的是"策略"**。谁的请求优先插入、chunk 给多大、显存到哪条线触发抢占——全部静态。这就出现一个很清晰的升级路径：让策略参数本身随运行时统计调整（比如按 TTFT——Time To First Token，用户等到第一个字的时间——的分布动态调 chunk 预算、按抢占频率切换 swap/recompute 偏好；swap = KV 搬去 CPU 内存、recompute = 丢 KV 重算，详见 5.2）。数据库的自适应执行（AQE）踩过的坑在这里可以直接预警：**统计波动会引起策略抖动**，在 serving 里表现为 KV 反复换入换出的 livelock（活锁：一直在搬数据，谁也没真正推进）——护栏（滞后、阈值带宽）是现成的，缺的是把这套环路建起来的人。

### 5.2 KV cache 分页：一切决策都已"代价化"，就差一个决策器

PagedAttention（SOSP'23）把 KV 切成固定 block（典型 16 token/块），按需分配、块表映射（思路与操作系统虚拟内存的分页/页表同构：逻辑连续、物理离散），碎片率从接近"预留最大长度"模式的 60–80% 降到个位数。这是推理栈到目前为止最漂亮的一笔工程。

有意思的是它之后的一系列决策，每一个**天然都是代价问题，却全部以固定策略实现**：

- **preemption 的抉择**：显存耗尽时牺牲一个 running 请求，两种代价——recompute（丢 KV，回来时重算 prefill，代价随 prompt 长度线性）vs swap（KV 搬去 CPU，代价是 PCIe 往返加换入延迟）。牺牲谁、用哪种方式，今天写死在调度器里。这长得就像一个 cost-based eviction 问题：数据库 buffer pool（缓冲池——同一个"内存放不下、逐出谁"的问题）从 LRU 走到代价感知逐出用了二十年，而 KV 逐出的代价甚至**更容易估算**——重算 prefill 的 FLOP 是显式的、swap 的字节数是已知的。
- **prefix caching**：共享前缀（system prompt、few-shot）的 KV 块复用，是"显存换计算"的缓存决策，命中收益（省掉的 prefill）与容量成本（挤占的 active KV）都是可算的；今天靠简单的淘汰规则管理。
- **准入水线**：给 decode 预留多少 block（watermark）、waiting 里谁先上——本质是"吞吐 vs 延迟"的显式权衡，今天是一个常数。

一块显存，三类决策，全部可代价化，全部静态。这是三处空白里我认为最可能先被填上的一处。

### 5.3 融合的两条路线：手写的天花板，编译器的地板

kernel 层和编译层其实在赛跑同一段路：**减少 HBM 往返**。融合的收益账很干净——逐算子执行时每个中间张量都要落显存再读回，融合后数据只在 kernel 入口/出口各过一次；RMSNorm（一种逐行归一化算子，LLM 每层都用）拆开算要 7 趟显存访问，融合后 2 趟，理论收益 3.5 倍上限（这是我的纸面账本，W6 会实测对账）。

两条路线的战绩很有意思：

- **手写路线**拿走了所有标志性战果。FlashAttention 是教科书案例：attention 的 softmax 需要全局归一化，朴素实现要么把整个序列的中间量落显存（O(N²) 显存往返）、要么分块后无法正确归一；FlashAttention 的解法是 online softmax——维护 running max \(m\) 与 running sum \(l\)，每处理一个新块先算 rescale 因子 \(\alpha = \exp(m_{old} - m_{new})\) 修正历史累积（记账的说法：新块里出现更大的数、换了对账基准，就把老账按新基准整体折算，再记新账）——从而把"归一化"改造成流式递推，attention 从显存复杂度 O(N²) 降到 O(N)，且精确等价。这是"通过算法重构消除显存往返"的典范，不是简单拼算子。
- **编译器路线**拿走了覆盖面。Inductor 能对任意 nn.Module 自动融合点式算子和归约，无需人工。但它的融合决策是结构规则（见空白一），对形状不敏感；而 GPU kernel 的代价恰恰对形状极度敏感——roofline 拐点、Tensor Core（GPU 的专用矩阵乘单元）的形状约束、occupancy（计算资源的占用率）都随形状变。

两条路线中间的那块地——**形状感知的、代价驱动的自动融合决策**——目前两边都没占到。手写路线知道天花板在哪但不可规模化，编译路线可规模化但摸不到天花板。

## 六、共享的成本语言：账本思维

上面所有分析其实只用了一种语言：**算账**。bytes 搬多少趟、FLOP 花多少、拐点在哪一侧、收益上限几倍——推理优化的核心技能是维护这几本账（带宽账、算力账、显存账、通信账）并在冲突时知道哪本主导。

这也是我认为这块空白值得人去做的原因：代价结构全部显式可算（不依赖端到端黑盒 profiling 就能推个大概），决策空间又小。**可估算 + 可枚举 + 未接入**——这是工程上最舒服的攻坚位置。

## 七、十周验证计划：把判断变成证据

以上论断目前的状态是"分析 + 源码初步阅读"。要立住，需要亲手数据。我排了一个十周计划（2026-10-19 至 12-27），三条设计原则：

1. **每个假设配一个动手验证**：判断融合"无代价模型"，就读 fusion pass 源码 + 做行为对照实验（构造两个仅形状不同的算子链，看融合决策是否无差别）；判断调度"策略静态"，就自写纯 Python 调度模拟器量化 continuous batching 与 preemption 的收益，再到真实 serve 环境验证。
2. **数值在 Mac 验证，性能在租的 GPU 上测**（Triton 有 interpret 模式，纯 Python 跑 kernel 对数值，正确性不花 GPU 小时）；租卡按"会话制"集中使用，五场各 3–5 小时，会话纪律只有一条：**绝不在计时区间里 debug**。
3. **产出物是"幼稚清单"**：读源码每发现一个"我觉得幼稚的决策"，记成结构化条目——具体决策、证据位置、"如果是我会怎么做"。十周后被实测砸实的条目，就是第二篇的选题库。

## 八、边界与自我反驳

写分析文章最忌布道。三条反方论点我认为足够硬，必须放正文：

1. **推理的计算图是固定的**。优化器方法论最锋利的部分（在巨大计划空间里搜索）面对的是一个 decoder layer 的固定循环，枚举空间天然小——"枚举"在这可能是屠龙刀杀鸡。
2. **尾延迟敏感性**。serving 里"换策略"的瞬时代价直接打在 P99（99 分位时延——最慢那 1% 请求的体验线）上，比批处理场景贵得多；反馈环路引入的抖动可能吃掉它带来的收益。
3. **领域迭代速度**。推理栈几乎每季度重写一次重要子系统（vLLM 的 V0→V1 即是），方法论沉淀可能永远追不上推倒重写。

以及一条正方回应，也是我最想验证的猜想：**正因为负载结构固定，成本估算反而更可控**——不用面对任意输入，只需要面对一个已知网络。三处空白也许不是"难所以没人做"，而是"还没轮到"。

## 九、结语

LLM 推理栈三四年长完了别的系统二十年的路，剩下的都是硬骨头：手写 kernel 卷到 attention 之外的边际收益递减，编译器的规则融合摸到形状敏感性这堵墙，调度器的启发式在长上下文与高并发下开始互相打架。

而"用代价估算选策略"这件事，在这套栈的三个位置——融合决策、并行度选择、KV 逐出——都精确地空着，且空位的形状一致：**代价可算、空间可搜、就是没人接**。

十周后，我带着幼稚清单和实测数据回来写第二篇：这三处空白，哪些被证据砸实了，哪些是我看走了眼。
